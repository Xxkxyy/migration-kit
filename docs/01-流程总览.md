# 01 · 整体流程总览

> 这一篇回答三个问题：**分几步、为什么是这个顺序、每步什么算"过关"**。
> 具体命令与参数见 `02-阶段详解.md`。

---

## 一、总体思路

不做"搬到一半两套并行跑"的复杂方案，采用 **"源端只读 → 目标端重建 → 数据灌入 → 全量校验 → 一次性切流"** 的单向搬运。

四条硬原则：

| 原则 | 含义 | 具体落地 |
|---|---|---|
| **源端只读** | 旧机全程不写入、不删除、不卸载 | 只执行 `rsync`/`mysqldump`/`docker inspect`，绝不 `DELETE`/`rm`/`docker rm` |
| **可回退** | 任何时刻旧系统都能立刻恢复服务 | 旧容器只 `stop` 不 `remove`；旧库不做任何 DDL |
| **可重跑** | 中途失败不需从头再来 | 每个长任务都有进度文件 / rc 对账 / 幂等策略 |
| **先验后切** | 没有证据不切流 | 每个阶段有明确验收命令与判定阈值 |

## 二、九个阶段

```
阶段0 勘查      阶段1 盘点      阶段2 环境+镜像      阶段3 文件搬运
   │               │                 │                    │
   └── 网络/凭据 ──┴── 服务清单 ─────┴── 镜像可用 ─────────┴── 字节级一致
                                                              │
阶段7 配置改指 ◄── 阶段6 应用重建 ◄── 阶段5 数据库灌入 ◄──────┘
   │                 │                  │
   └── 无旧IP残留 ───┴── 容器全 Up ────┴── 行数/对象数一致
                          │
                    阶段8 端到端验收
                          │
                    阶段9 切流（需业务停机窗口）
```

### 阶段 0 · 勘查（0.5 天）

| 项 | 内容 | 判据 |
|---|---|---|
| 连通性 | 新旧机器 22/业务端口是否可达 | 全部 `Test-NetConnection` / `nc` 通 |
| 凭据 | 每台机器 root 口令是否可用、是否含特殊字符 | 逐台 SSH 登录成功 |
| 网络拓扑 | 新旧是否同二层（VLAN）、网段、网关 | `ip neigh` 能否 ARP 到对端网关 |
| 存储 | 新机磁盘容量、是否需 LVM 合并 | 目标容量 ≥ 源端 × 1.3 |

> **本次教训**：新旧分属两个 VLAN，`ping` 通但 ARP 不通 → 不能简单换 IP。
> 结论必须用 `arping`/`ip neigh` 验证，不能只看 `ping`。

### 阶段 1 · 盘点（0.5 天）

产出一张"资产—服务"矩阵：

- OS 版本、内核、时区、字符集
- 磁盘：`df -h`、`lsblk`、挂载点、可用空间
- Docker：版本、存储驱动、镜像列表（含 IMAGE ID）、容器清单（名称/镜像/端口/挂载/环境变量/重启策略）
- 端口：`ss -lntp` 与容器映射对照
- MySQL：版本、datadir、字符集、库清单、每库表数、大表 TopN、账号与授权主机段
- 应用配置：哪些文件写了 IP/域名（`grep -rl`）
- 外部依赖：Oracle/Redis/MQ/对象存储/第三方接口

> 盘点的价值不是"看一眼"，而是**生成后续脚本的输入**。
> `01_survey.py` 的输出建议直接存成 `inventory.md` 存档，切流后排查用得上。

### 阶段 2 · 目标环境 + 镜像（1 天）

1. 装 Docker（版本可高于源端）
2. 源端 `docker save` → `scp` → 目标端 `docker load`
3. **逐个比对 IMAGE ID**，不要只看 tag
4. 大镜像（>2 GB）用 `pigz` 并行压缩，否则 1 Gbps 网卡下传输时间会失控

验收：`docker images --format '{{.Repository}}:{{.Tag}} {{.ID}}'` 两侧完全一致。

### 阶段 3 · 文件数据搬运（0.5~2 天，取决于体量）

- 用 `rsync -a --numeric-ids`，保留属主/权限/时间
- **先 `--dry-run` 看差异规模**，再实跑
- 大目录分批（按子目录），失败只重跑该批
- 校验不靠"rsync 没报错"，而靠：**文件数 + 文件字节总和** 两侧一一相等

验收：
```
find <dir> -type f | wc -l                     # 文件数
find <dir> -type f -printf '%s\n' | awk '{s+=$1} END {print s}'   # 字节总和
```
两侧数字完全相同才算过。

> **本次教训**：`rsync --delete` 绝对不要用；源端 00:00 会做日志轮转，最后一次比对必然有几个日志文件对不上，属正常，记录说明即可。

### 阶段 4 · 数据库对象建模（0.5 天）

顺序很重要：**库 → 表结构 → 数据 → 索引 → 视图/例程 → 账号授权**。

- 库：按源端 `SHOW CREATE DATABASE` 的字符集/排序规则逐个建
- 表结构：`mysqldump --no-data --routines=false --triggers=false`
- 数据：见阶段 5
- 索引：大表导入时**先不建二级索引**，数据灌完再建
- 账号：`SHOW GRANTS` 导出后重放，**注意授权主机段是 IP 段**（换网段必须改）
- 视图/例程/触发器：单独 dump

验收：`information_schema.tables` 两端口径一致（表数、视图数、例程数）。

### 阶段 5 · 数据灌入（1~3 天，最大变量）

分三档处理，不要一刀切：

| 档位 | 判定 | 做法 |
|---|---|---|
| 小表（< 100 MB） | 单表 dump 秒级 | `mysqldump | mysql` 串行 |
| 中表（100 MB ~ 5 GB） | 分钟级 | 4~8 并发，按表切分 |
| 大表（> 5 GB 或 > 1000 万行） | 小时级 | **按主键区间切片 + 8 并发 + 索引后建** |

关键动作（缺一不可）：

1. 导入期 `my.cnf`：`flush=0`、`doublewrite=0`、`O_DIRECT_NO_FSYNC`、`skip-log-bin`
2. 大表先 `DROP INDEX`（保留 PRIMARY）
3. 切片边界**从源端取**（目标端 TRUNCATE 后 MIN/MAX 是 NULL）
4. 每个分片远端 `setsid` 独立执行 + 写 `rc` 文件
5. 全部分片 `rc=0` 后：`ADD INDEX` → `ANALYZE TABLE`
6. 行数与源端 `COUNT(*)` 比对（抽样 + 关键表全量）
7. 切生产参数：`flush=2`、`doublewrite=1`、`log_bin=1`、**`innodb_stats_auto_recalc=ON`**

验收：大表行数完全一致；`mysql.innodb_table_stats` 里非空表 `n_rows` 全部 > 0。

### 阶段 6 · 应用重建（0.5 天）

不要手写 `docker run`，用源端 `docker inspect` 的**真实定义**重建：

- 镜像、网络、挂载、环境变量、端口、工作目录、启动参数原样复制
- **Entrypoint 与 Cmd 只传一套**：镜像自带 ENTRYPOINT 时只传 Cmd，否则会变成 `java java -jar`
- 挂载路径按目标端实际目录修正（本次踩坑：rabbitmq 挂到了空目录）
- 按依赖顺序启动：注册中心 → 缓存 → MQ → 网关 → 业务服务 → 前端 nginx

验收：`docker ps -a` 里 0 个非 Up；注册中心服务数 = 预期数。

### 阶段 7 · 配置改指（0.5 天）

把所有写死旧 IP 的地方改到新 IP：

- 应用 `bootstrap*.properties`（注册中心地址、JDBC、Redis、MQ）
- 网关路由、nginx `proxy_pass`
- SeaweedFS master/volume 的 `-ip`、`-master` 参数、compose 命令串
- 数据库授权主机段（`'user'@'10.0.0.%'` → `'user'@'10.1.0.%'`）
- 客户端（桌面程序）的 `*.json` 配置

验收：目标端 `grep -rl '旧网段' /data /opt /etc` 结果必须为空（`.bak_ip` 备份文件除外）。

### 阶段 8 · 端到端验收（0.5 天）

四层验证，逐层向上：

1. **进程层**：容器全 Up
2. **注册层**：注册中心服务数、实例数、健康状态
3. **接口层**：从外部经 nginx → 网关 → 业务，拿到**应用自己的业务响应**（不是 502/504）
4. **数据层**：抽样查询命中、附件下载、报表数据

> 判定标准：`/authserver/oauth/token` 返回 401 + 自定义 `serial` 头，说明整条链路活着；
> 返回 502/504 说明网关后面还有服务没起来。

### 阶段 9 · 切流（需停机窗口，约 20 分钟）

1. 停旧容器（**只 stop，不 rm**）
2. 最后一次增量 `rsync`（只传停写后的差异）
3. 冒烟：端口 → 注册中心 → 登录 → 关键业务接口
4. 客户端/域名切到新地址
5. 旧机保持关机不销毁，观察 1~2 周

回退预案：任何一步异常 → 启动旧容器，回退时间 < 5 分钟。

## 三、时间线（本次实测）

| 日期 | 阶段 | 实际耗时 | 卡点 |
|---|---|---|---|
| D1 上午 | 0 勘查 + 1 盘点 | 4 h | 凭据口径不一致（221 独立口令） |
| D1 下午 | 2 环境 + 镜像 | 6 h | 大镜像 3.2 GB 传输 |
| D1 夜 | 3 文件搬运 | 9 h | 1.97 TB / 千兆网 ≈ 60 MB/s |
| D2 全天 | 4 建模 + 5 小中表 | 14 h | 慢盘 fsync，116 行/秒 |
| D3 全天 | 5 大表 | 26 h | 反复调参，见 03-坑位 |
| D4 上午 | 5 收尾 + 生产参数 | 5 h | 统计信息遗漏（后期才暴露） |

## 四、五个必须停下来确认的决策点

| # | 决策点 | 本次选择 | 理由 |
|---|---|---|---|
| 1 | 数据库物理搬迁还是逻辑重建 | **逻辑重建**（dump/load） | 跨大版本、跨字符集、需要改参数，物理拷贝风险高 |
| 2 | 应用机 1:1 还是重新规划 | **1:1 映射** | 配置里写死了本机 IP/挂载，重新规划改动面太大 |
| 3 | 换 IP 还是改客户端 | **改客户端**（先做 L2 验证再决定） | 实测两网段不同广播域，换 IP 需网络侧配合 |
| 4 | 大表切片按什么维度 | **主键区间** | 无主键表单独处理，用 `OFFSET` 会越翻越慢 |
| 5 | 切流方式 | **停旧 → 增量 → 起新** | 旧系统本身已不健康（Redis 掉线数月），不存在真实流量切换 |

## 五、与"教科书迁移"的三点不同

1. **不相信 `information_schema` 的统计**：本次源库 `T_SignData` 报 887 万行、实际 1852 万；`T_External_Business_Log` 报 18.6 GB、实际 321 GB。**一切以 `COUNT(*)` 和文件字节数为准。**
2. **不追求"零停机"**：旧系统已经带病运行，追求零停机只会把风险叠到新系统上。宁可一个 20 分钟窗口。
3. **迁移不是搬运，是修复**：搬完必须做一轮"性能基线校准"（统计信息、缺失索引、慢查询），否则新系统"能跑但不好用"。
