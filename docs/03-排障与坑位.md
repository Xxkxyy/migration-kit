# 03 · 排障与坑位（全部来自真实事故）

> 每条格式：**现象 → 根因 → 处置 → 可复用结论**。
> 按"杀伤力"排序，前 5 条是会真停服的。

---

## P1 · `ps | grep '[_x]'` 把全机进程杀光 🔴

**现象**
执行"停止重复导入脚本"的清理命令后，目标机瞬间失联，`systemd(PID 1)`、`sshd`、`mysqld`、`dockerd` 全部消失，只能重启机器。

**根因**
```bash
ps -ef | grep '[_rebuild2.sh]' | awk '{print $2}' | xargs kill -9
```
方括号在**正则**里是字符类，不是"字面量括号"。`[_rebuild2.sh]` 匹配的是"任意一个属于 `_ r e b u i l d 2 . s h` 的字符"，几乎命中所有进程。

**处置**
- 精确匹配：`pkill -x <进程名>`、`pkill -f '^/bin/bash /data/_mig/rebuild2\.sh$'`
- 或先 `ps -eo pid,args` 打印，人工确认 PID 再 kill

**可复用结论**
> 任何"批量 kill"必须能打印出**待杀清单**并能人工复核。
> 禁止在生产机上一次管道直接 `xargs kill -9`。

## P2 · 统计信息归零，业务查询从毫秒变 90 秒 🔴

**现象**
- 护士站病人列表：**93 秒 / 27 秒**，偶尔网关 **504 Hystrix Read timed out**
- 护理记录详情：**30 分钟**不返回
- 慢日志里出现"扫描 1314 万行、返回 0 行"的查询

**根因**
导入期把 `innodb_stats_auto_recalc` 设为 `OFF`，切生产参数时**漏改回 ON**。
`mysql.innodb_table_stats` 里 `ek_patient` 的 **215 张表 n_rows 全为 0**（实际 726 GB），
优化器认为所有表都是空表，于是选择全表扫描 / 错误的 join 顺序。

**处置**
```sql
SET GLOBAL innodb_stats_auto_recalc=ON;   -- 并写入 my.cnf
SET GLOBAL innodb_stats_on_metadata=OFF;  -- 保持, 避免 I_S 查询触发重算
ANALYZE TABLE <每一张非空表>;
```
验证：
```sql
SELECT COUNT(*) FROM mysql.innodb_table_stats s
JOIN information_schema.tables t
  ON t.table_schema=s.database_name AND t.table_name=s.table_name
WHERE s.n_rows=0 AND t.data_length>20000
  AND s.database_name NOT IN ('mysql','sys');   -- 必须为 0
```

**可复用结论**
> "统计信息"必须写进切换清单，与 `flush`/`doublewrite` 同级对待。
> 判断标准不是 `data_length`，而是 **非空表的 `n_rows` 是否 > 0**。
> 空表 `data_length=16384` 且 `n_rows=0` 属正常，不要误判。

## P3 · `information_schema` 统计严重失真，切片方案全错 🔴

**现象**
按 `TABLE_ROWS` 估算切片，导入后行数对不上；按 `data_length` 估算容量，磁盘提前写满。

**根因**
源库长期未 `ANALYZE`，且 `innodb_stats_auto_recalc=OFF`：
- `T_SignData` 报 887 万行 → 实际 **18,525,216 行**
- `T_External_Business_Log` 报 18.6 GB → 实际 **321 GB**
- `CARDINALITY` 出现 `1` 这种不可能值

**处置**
- 一切以 `SELECT COUNT(*)` 为准（长耗时也要跑）
- 容量以 `du -sh <datadir>/<db>` 为准
- 切片边界用 `MIN(id)/MAX(id)`，不用估算行数均分

**可复用结论**
> 迁移前的"体量评估"必须用两条硬命令：`COUNT(*)` 和 `du -sh`。
> 任何基于 `TABLE_ROWS` 的容量/时间预估都要打 3 倍余量。

## P4 · `INSERT IGNORE` + 反复重试把表撑到 11~14 倍 🔴

**现象**
表体积异常膨胀，行数远超源端。

**根因**
分段失败后重试，但重试前没清空该段，`INSERT IGNORE` 只跳过主键冲突，对无唯一约束的行会重复插入；
叠加 `unique_checks=0` 后连唯一索引都不校验。

**处置**
- 放弃"重试叠加"，改为 **TRUNCATE 整表 + 单次分段**
- 重试改用 `mysqldump --insert-ignore`（幂等）
- 完成后必须 `COUNT(*)` 比对

**可复用结论**
> "幂等"不等于"重试安全"。批量装载的幂等要么靠主键唯一约束，要么靠先清空。

## P5 · 分段 RC=0 但导了 0 行 🟠

**现象**
所有分片返回成功，目标表却一行没有。

**根因**
脚本先 `TRUNCATE`，再从**目标表**取 `MIN(id)/MAX(id)`——此时表已空，边界是 `NULL`，
`--where="id >= NULL"` 匹配不到任何行，但 `mysqldump` 退出码是 0。

**处置**
边界一律从**源端**取：
```bash
INFO=$(mysql -h<源端> -e "select min(id), max(id) from $DB.$TB")
```

**可复用结论**
> "命令成功"不等于"业务成功"。每个批量任务必须有一个**结果校验点**（行数/校验和）。

## P6 · SSH 半死连接让工作线程永久阻塞 🟠

**现象**
并发导入的 7 个线程集体"静默死亡"：不报错、不退出、也不推进。

**根因**
`paramiko` 的 `recv_exit_status()` **没有超时**。TCP 半开时它会永久等待；
`exec_command(timeout=...)` 只管 channel 读超时不保证唤醒。

**处置**
```python
def run_t(conn, cmd, timeout):
    box = {}
    def _f():
        box["r"] = run(conn, cmd, timeout)
    th = threading.Thread(target=_f, daemon=True)
    th.start(); th.join(timeout + 15)
    if th.is_alive():
        drop_conn();            # 丢弃这条连接
        return -2, "", "TIMEOUT"
```
另外：`transport.set_keepalive(20)` 保活。

**可复用结论**
> 任何"可能不返回"的网络调用，都要用"旁路线程 + join 超时 + 丢弃连接"三件套。
> 旁路线程里**不能**再取新的连接（thread-local 会新建并泄漏）。

## P7 · 本地 SSH 断了，远端任务还在跑，形成重复作业 🟠

**现象**
超时后本地脚本退出，但远端 `mysqldump|mysql` 还在跑；重跑一次 → 两个作业抢同一张表。

**处置**
- 远端 `setsid nohup <script> &` 独立执行，与 SSH 会话解耦
- 每个分片写 `rc` 文件，本地只做"轮询对账"
- 脚本入口加 `flock -n 9`，重复启动直接退出

```bash
exec 9>/data/_mig/job.lock
flock -n 9 || { echo "另一实例在跑"; exit 0; }
```

**可复用结论**
> 长任务的所有权必须"在远端"，本地只是观察者。

## P8 · Docker 重建后 `weed weed server` / `java java -jar` 🟠

**现象**
容器启动即退出，日志首行 `unknown subcommand "weed"`。

**根因**
镜像自带 `ENTRYPOINT ["/usr/bin/weed"]`，重建时把 `Cmd` 与 `Entrypoint` **都**拼进去，
最终命令变成 `weed weed server ...`。

**处置**
只传 `Cmd`；仅当镜像没有 ENTRYPOINT 时才显式指定。

**可复用结论**
> 重建容器前先看 `docker inspect -f '{{.Config.Entrypoint}} | {{.Config.Cmd}}'`，
> 二者只会拼一次。

## P9 · 配置改了，服务仍用旧 IP 🟠

**现象**
批量替换了 `bootstrap.properties`，容器重启后仍连旧地址。

**根因**
两类遗漏：
1. 容器 `Env` 里的地址来自 `docker run -e`，不读配置文件 → 必须重建容器
2. `Cmd` 参数里的地址（如 SeaweedFS `-master=<旧IP>:9333`）不会被文件替换覆盖

**处置**
阶段 6 重建时对 `Env` 和 `Cmd` 都做 IP 替换，然后**重建容器**（不是 restart）。

**可复用结论**
> "改配置"要覆盖三个位置：文件、容器 Env、启动命令参数。

## P10 · RabbitMQ 启动后业务全部 `ACCESS_REFUSED` 🟠

**现象**
`busi_*` 服务卡在 `RabbitListener`，日志 `ACCESS_REFUSED - Login was refused`。

**根因**
三个叠加：
1. vhost `scloud-release` 不存在（新节点是空 mnesia）
2. 业务账号是 `newhis/newhis`，不是 `guest`
3. `guest` 默认仅允许 localhost

**处置**
```bash
rabbitmqctl add_vhost scloud-release
rabbitmqctl add_user newhis newhis
rabbitmqctl set_permissions -p scloud-release newhis ".*" ".*" ".*"
```

**可复用结论**
> 中间件迁移后必须**按业务账号实际值**验证一次，不能只看容器 Up。

## P11 · RabbitMQ 挂载了空目录，数据"丢了" 🟠

**现象**
容器起来后所有 vhost/队列为空，像是全新节点。

**根因**
compose 里挂的是 `/data/vol/<hash>`，而真实 mnesia 在 `/data/app/rabbitmq-data`。

**处置**
以 `docker inspect` 里的 `Binds` 为准，逐条 `ls` 确认真实数据目录。

## P13 · Windows 侧脚本带 CRLF，远端 `bash` 报 `$'\r': command not found` 🟡

**处置**
- 生成脚本时 `open(..., "w", newline="\n")`
- 上传后 `sed -i 's/\r$//'`

## P14 · SQL 里的反引号被 shell 当命令替换 🟡

**现象**
`CREATE DATABASE \`ek_patient\`` 执行后库名变成空或报错。

**根因**
反引号在 bash 里是命令替换。

**处置**
- SQL 写入 `.sql` 文件再 `mysql < file.sql`
- 或 heredoc 用 `<<'EOF'`（带引号）禁止展开

## P15 · PowerShell 解析 `2>/dev/null`、`$()`、`$_` 🟡

**现象**
本地执行 Python/SSH 命令时随机报错、PSReadLine 崩溃。

**处置**
- 所有远端命令写进 `.py`/`.sh` 文件再执行，不在 PowerShell 里内联长命令
- `Select-Object -First N` 会**提前终止管道**导致输出截断，改用文件日志

## P16 · 密码含全角标点，SSH 认证必然失败 🟡

**现象**
手工能登录，脚本报 `Authentication failed`。

**根因**
口令里的 `！`（全角）与 `!`（半角）字节不同。

**处置**
逐字节确认口令；配置里统一用半角。

## P17 · 导入期间跑 `COUNT(*)` 把 ANALYZE 卡死 🟡

**现象**
`ANALYZE TABLE` 状态长期 `Waiting for table flush`。

**根因**
另有大表 `COUNT(*)` 全表扫描占着表，`ANALYZE` 需要 MDL 升级，被阻塞。

**处置**
- 先查 `information_schema.processlist` 找 `time` 很大的查询
- 确认无业务影响后 `KILL <id>`
- `ANALYZE` 用 `timeout 300` 包一层，避免单表卡死拖住整轮

```sql
SELECT id, time, state, LEFT(info,60)
FROM information_schema.processlist
WHERE command='Query' AND time>120;
```

## 附：三个"看起来像故障、其实不是"的现象

| 现象 | 真相 |
|---|---|
| `notice` 日志 `Handshake failed due to invalid Upgrade header` | 用普通 HTTP GET 访问 WebSocket 端点，Spring 的正确反应 |
| `notice` 日志 `向 ESB 注册服务失败。esb 地址: /` | ESB 未配置，该环境本就没有 ESB |
| 业务日志 `ERROR ... resp_log` 里带 `"exception":null` | 日志框架把每次响应都打 ERROR 级别，属于日志规范问题，不是异常 |
