## 事故 1 · 统计信息归零，业务从毫秒变 90 秒（P0）

### 现象
- 护士站登录后，病人列表转圈 **93 秒**，偶尔网关返回 **504 Gateway Timeout**
- 护理记录详情页 **30 分钟**不返回，前端直接断开
- 慢日志里出现"扫描 1314 万行、返回 0 行"的查询

### 影响
迁移验收已经被认为"完成"之后才暴露，属于**上线后才发现**的可用性事故。

### 时间线
| 时间 | 事件 |
|---|---|
| D3 | 导入期设置 `innodb_stats_auto_recalc=OFF`（减少导入时的统计开销） |
| D4 05:26 | 切生产参数：改了 flush / doublewrite / log_bin，**漏了 stats_auto_recalc** |
| D5 07:56 | 网关第一次 504 |
| D5 08:10~08:24 | 慢日志出现 93s / 27s / 938s 的查询 |
| D5 08:28 | 定位到 `mysql.innodb_table_stats` 里 215 张表 `n_rows` 全为 0 |
| D5 09:00 | ANALYZE 完成，非空表统计归零数 = 0 |

### 根因
`innodb_stats_persistent=ON` 时，优化器读的就是 `mysql.innodb_table_stats`。
导入期关闭了自动重算，导入完成后没有手动 `ANALYZE`，于是：
- 215 张表 `n_rows=0`
- 优化器认为每张表都是空的 → 选全表扫描 / 错误的 join 顺序
- `ek_patient` 实际 726 GB，全表扫描 = 分钟级到小时级

### 错误代码（当时的切换脚本）
```bash
sed -i \
 -e 's/^innodb_flush_log_at_trx_commit=0/innodb_flush_log_at_trx_commit=2/' \
 -e 's/^innodb_doublewrite=0/innodb_doublewrite=1/' \
 -e 's/^skip-log-bin/log_bin=.../' \
 /etc/my.cnf
systemctl restart mysqld
# ← 少了 innodb_stats_auto_recalc，也没跑 ANALYZE
```

### 修复代码
```bash
# 1) 参数回切（内存 + 文件双写）
sed -i 's/^innodb_stats_auto_recalc=OFF/innodb_stats_auto_recalc=ON/' /etc/my.cnf
mysql -uroot -e "set global innodb_stats_auto_recalc=ON"

# 2) 全库 ANALYZE（只处理失效的，最多 3 轮）
bash scripts/lib/stat_repair.sh

# 3) 验证（必须为 0）
mysql -uroot -N -e "select count(*) from mysql.innodb_table_stats s
  join information_schema.tables t on t.table_schema=s.database_name and t.table_name=s.table_name
  where s.n_rows=0 and t.data_length>20000 and s.database_name not in ('mysql','sys')"

# 4) 复核执行计划
mysql -uroot -D ek_patient -e "explain select ... "   # 期望 ref/range，不是 ALL
```

### 预防
1. **把 `ANALYZE` 写进切换脚本的最后一步**，与 flush/doublewrite 同级
2. 验收清单里加一条硬性检查："非空表 `n_rows=0` 的数量必须为 0"
3. 空表 `data_length=16384` 时 `n_rows=0` 属正常，不要误判为故障

### 可复用结论
> 导入期参数里，**性能类**参数（flush/doublewrite/change_buffering）可以忘，
> 但**优化器类**参数（stats_auto_recalc/stats_on_metadata）一忘就是业务级故障。

## 事故 2 · `ps | grep '[_x]'` 杀掉全机进程（P0）

### 现象
执行"停止重复导入脚本"的命令后，目标机瞬间失联。运维上台发现 `systemd(PID 1)`、`sshd`、`mysqld`、`dockerd` 全部消失，只能重启机器。

### 时间线
| 时间 | 事件 |
|---|---|
| T+0 | 发现有两次 `_rebuild2.sh` 在跑，想杀掉重复的那个 |
| T+1 | 执行 `ps -ef \| grep '[_rebuild2.sh]' \| awk '{print $2}' \| xargs kill -9` |
| T+2 | SSH 断开，所有端口不可达 |
| T+30min | 通过带外/控制台重启机器 |

### 根因
`[_rebuild2.sh]` 在**正则**里是字符类，匹配"任意一个属于 `_ r e b u i l d 2 . s h` 的字符"。
几乎每个进程路径都含 `/`、`s`、`h`、`e`…于是匹配到全机进程。

### 错误代码
```bash
ps -ef | grep '[_rebuild2.sh]' | awk '{print $2}' | xargs kill -9
```

### 修复代码
```bash
# 方式一：精确进程名
pkill -x rebuild2.sh

# 方式二：精确匹配完整命令行（注意 \. 与 ^$）
pkill -f '^/bin/bash /data/_mig/rebuild2\.sh$'

# 方式三：先打印、人工确认、再逐个杀
ps -eo pid,lstart,args | grep -F '/data/_mig/rebuild2.sh' | grep -v grep
# 确认无误后
kill -TERM <pid>
```

### 预防
1. 所有复用脚本写 `flock`，从源头避免"重复实例"
2. 批量 kill 必须**先打印清单**，能人工复核
3. 生产机禁止 `xargs kill -9` 一把梭

### 可复用结论
> 任何 `grep '[...]'` 都是字符类，不是字面量。要么转义成 `grep -F`，要么用 `pkill -x`。

## 事故 3 · `INSERT IGNORE` 反复重试把表撑到 14 倍（P0）

### 现象
某个分片失败后自动重试，最终表体积是源端的 11~14 倍，行数远超源端。

### 时间线
| 时间 | 事件 |
|---|---|
| D2 晚 | 分段导入，部分分片因主键冲突失败 |
| D2 夜 | 自动重试改为 `INSERT IGNORE` + `unique_checks=0` |
| D3 早 | 发现表 321 GB → 实际写入 4 TB 级（磁盘快满） |
| D3 午 | 尝试 `DELETE` 清理该区间：8 并发 26 分钟零吞吐，回滚又花 40 分钟 |
| D3 晚 | 放弃增量修补，改为"清空 + 单次分段 + 索引后建"重灌 |

### 根因
1. `INSERT IGNORE` 只跳过**唯一键冲突**，对无唯一约束的重复行照插
2. `unique_checks=0` 连唯一性都不校验，等于完全放弃去重
3. 重试前没有清空该段，于是"失败一次 = 多一份数据"

### 错误代码
```bash
# 重试时直接叠加
mysqldump --insert-ignore --where="id BETWEEN $A AND $B" db tb | mysql db
# 且之前执行过
mysql -e "set unique_checks=0; set foreign_key_checks=0"
```

### 修复代码
```bash
# 1) 彻底放弃"重试叠加"，改为一表一次性灌
mysql -e "truncate table db.tb"

# 2) 分段单次执行，每段自己的 rc
#    （脚本见 scripts/lib/bulk_table.sh）

# 3) 如必须重试，用 --insert-ignore 且**先删该段**
#    但慢盘上 DELETE 大区间不可行 → 实际上只能 TRUNCATE 重来

# 4) 完成后行数核对
mysql -N -e "select count(*) from db.tb"
```

### 预防
1. 批量装载前先明确幂等策略：**主键唯一 → 可重试；否则 → 必须清空**
2. 任何重试都必须先校验"目标端是否已有该段数据"
3. `unique_checks=0` 只允许用于"目标表已 TRUNCATE"的场景

### 可复用结论
> 慢盘上 `DELETE` 是最差的选择：逐行删、写 undo、可能回滚。
> 大表纠正一律"TRUNCATE + 重灌"，不要试图增量修补。

## 事故 4 · SSH 半死连接让 7 个线程静默死亡（P1）

### 现象
8 并发导入，7 个线程"既不报错也不推进"，只有 1 个在跑。重跑之后又出现重复作业。

### 根因
- `paramiko` 的 `recv_exit_status()` **没有超时**，TCP 半开时永久阻塞
- `exec_command(timeout=N)` 只是 channel 读超时，不能保证唤醒阻塞的线程
- 在"旁路线程"里又调用了 `conn()`（thread-local）→ 每次新建连接且不关闭，累计泄漏 948 条，把 sshd 拖死

### 错误代码
```python
def run(conn, cmd):
    _, o, e = conn.exec_command(cmd, timeout=60)
    o.channel.recv_exit_status()      # ← 可能永久阻塞
    return o.read()
```
```python
# 更糟：在超时线程里重新取连接
def _worker():
    c = conn()                        # thread-local，新建连接
    ...
```

### 修复代码
```python
def run(conn, cmd, timeout=120):
    box = {}
    def _worker():
        try:
            _, o, e = conn.exec_command(cmd, timeout=timeout)
            o.channel.recv_exit_status()
            box["r"] = (0, o.read().decode(), e.read().decode())
        except Exception as exc:
            box["r"] = (-1, "", repr(exc))
    th = threading.Thread(target=_worker, daemon=True)
    th.start()
    th.join(timeout + 15)
    if th.is_alive():
        conn.close()                  # 连接已不可信，必须丢弃
        return -2, "", "HARD_TIMEOUT"
    return box["r"]
```

### 预防
1. 连接缓存在**调用者线程**取好再传入旁路线程（不要在旁路线程里取）
2. `transport.set_keepalive(20)`
3. 超时后一律 `drop_conn()`，不复用

### 可复用结论
> "网络调用 + 无超时" = 线程池慢性死亡。
> 超时三件套：旁路线程、join 超时、丢弃连接。

## 事故 5 · 分段 RC=0 但导了 0 行（P1）

### 现象
8 个分片全部返回 `rc=0`，目标表却是空的。

### 根因
脚本顺序是：先 `TRUNCATE`，再从**目标表**取 `MIN(id)/MAX(id)`。
TRUNCATE 之后表为空 → 边界是 `NULL` → `--where="id >= NULL"` 匹配不到行 → `mysqldump` 正常退出（0 行）。

### 错误代码
```bash
mysql -e "truncate table $DB.$TB"
BOUND=$(mysql -N -e "select min(id), max(id) from $DB.$TB")   # ← 目标端，此时是 NULL
mysqldump --where="id >= $LO and id <= $HI" ...
```

### 修复代码
```bash
# 边界必须从源端取
BOUND=$(mysql -h$SRC -uroot -p$PW -N -e "select count(*), ifnull(min(id),0), ifnull(max(id),0) from $DB.$TB")
TOTAL=$(echo "$BOUND" | cut -f1)
LO=$(echo "$BOUND"    | cut -f2)
HI=$(echo "$BOUND"    | cut -f3)
[ -z "$TOTAL" ] && { echo "取边界失败"; exit 1; }
```

### 预防
每个批量任务必须有**结果校验点**：行数 / 校验和 / 抽样命中，不能只看退出码。

### 可复用结论
> 退出码只说明"命令没报错"，不说明"业务做对了"。
> 任何 dump→load 都必须跟一次 `COUNT(*)`。

## 事故 7 · 导入只有 116 行/秒（P1，时间成本最大）

### 现象
`mysqldump | mysql` 单表 116 行/秒，按这个速度 1852 万行要 44 小时。

### 定位过程
```bash
# 1) 测存储（结果：4K 同步写 1.3 IOPS，每次提交等 0.73 秒）
dd if=/dev/zero of=/tmp/io bs=4k count=500 oflag=direct,dsync

# 2) 看 InnoDB 在等什么
mysql -e "show engine innodb status\G" | grep -A5 'FILE I/O'
```

结论：**每插入一行提交一次，每次提交两次 fsync（redo + doublewrite）**，慢盘上每次 0.7 秒 → 数据必然按行算。

### 修复（四层，逐层叠加）

```ini
# 第 1 层：参数（提速 28 倍，116 → 3000+ 行/秒）
innodb_flush_log_at_trx_commit=0
innodb_doublewrite=0
innodb_flush_method=O_DIRECT_NO_FSYNC
innodb_change_buffering=none
```

```bash
# 第 2 层：索引后建（再提速 15 倍，单表 240 → 3500 行/秒）
# 导入前
ALTER TABLE db.tb DROP INDEX <每一个二级索引>;
# 导入后
ALTER TABLE db.tb ADD INDEX <...>;
ANALYZE TABLE db.tb;
```

```bash
# 第 3 层：主键区间切片 + 8 并发
# 边界从源端取，每段 setsid 独立执行，rc 对账
```

```bash
# 第 4 层：与 rsync 错峰（两者同时跑会互相抢 IO）
# 先把文件同步做完，再开始灌库
```

### 效果
| 阶段 | 速率 | 说明 |
|---|---|---|
| 原始 | 116 行/秒 | 每行 2 次 fsync |
| +参数调优 | ~3000 行/秒 | 去掉每次提交的 fsync |
| +索引后建 | ~3500 行/秒 | 不再为每行做随机索引写 |
| +8 并发 | 整体 2.8 万行/秒 | 受限于磁盘总带宽 |

### 可复用结论
> 大表导入的瓶颈通常不是 CPU、不是网络，而是**每次提交的 fsync**。
> 先测 4K 同步写 IOPS，再决定参数；不要盲目调 `innodb_buffer_pool_size`。

## 事故 8 · `ping` 通 ≠ 同二层，差点换 IP 失联（P2）

### 现象
计划"新旧服务器互换 IP"。两侧互相 `ping` 都通，判断"可以直接改 IP"。
在正式改之前做了一次试挂地址，才发现根本不通。

### 根因
- 两个网段由**同一台 L3 设备**（MAC 相同）路由，所以 `ping` 通
- 但分属**两个广播域（VLAN）**，把 50 段地址挂到 51 段的网卡上，连网关的 ARP 都收不到

### 错误判断方式
```bash
ping -c2 10.1.0.196      # 通 → 误判"可以直接换 IP"
```

### 正确判断方式
```bash
# 临时挂一个对端网段地址，看能不能 ARP 到对端网关
ip addr add 10.0.0.250/24 dev ens7
ping -c2 -W2 -I 10.0.0.250 10.0.0.254
ip neigh show 10.0.0.254        # REACHABLE=同二层；INCOMPLETE/FAILED=不同 VLAN
ip addr del 10.0.0.250/24 dev ens7
```

### 结论与处置
- 不同二层 → **放弃换 IP**，改为：改客户端配置（本次最终方案）或网络侧 DNAT
- 如果没做这一步，直接改 IP 会导致 5 台机器全部失联，只能带外恢复

### 可复用结论
> 判断"能否换 IP"，`ping` 只能证明路由可达，**必须用 ARP 证明广播域相同**。
> 任何网络变更前，先用临时地址试挂一次。

## 事故 9 · Oracle 驱动注入把 Spring Boot 应用搞挂（P1）

### 现象
manager 需要访问 Oracle（动态数据源，配置在 `ek_manager.T_dbResource` 表里），但 fat jar 内没有 ojdbc。
用 `jar uf` 把 `ojdbc8.jar` 塞进 `BOOT-INF/lib/` 之后，容器**启动即退出**：

```
Unable to open nested entry 'BOOT-INF/lib/ojdbc8.jar'
	at org.springframework.boot.loader.jar.JarFile.createJarFileFromEntry(JarFile.java:262)
```

### 根因
Spring Boot 的嵌套 jar **必须以 STORED（不压缩）方式存放**，Launcher 才能随机定位。
`jar uf` 默认 deflate 压缩，所以条目虽然进去了，但不可读。

### 错误代码
```bash
cd /tmp/inj && jar uf app.jar BOOT-INF/lib/ojdbc8.jar      # ✗ 默认压缩
```

### 修复代码
```bash
# 1) 先恢复原 jar，把服务拉起来（保命优先）
cp -p sshapp-manager.jar.bak_oracle sshapp-manager.jar
docker start busi_manager_1

# 2) 用 -0（store only）重新注入
cd /tmp/inj2 && jar uf0 app.jar BOOT-INF/lib/ojdbc8.jar

# 3) 必须校验：Method 列要为 Stored
unzip -v app.jar | grep ojdbc8.jar
#   4210517  Stored  4210517   0%  ...  BOOT-INF/lib/ojdbc8.jar

# 4) 完整性 + 替换 + 重启
unzip -t app.jar >/dev/null && docker cp ... && docker restart busi_manager_1
```

### 验证驱动真的能被加载（不要只看文件在不在）
```bash
# 用 jar 自己的类加载器跑一个连接测试，driver 必须从 BOOT-INF/lib 里被找到
java -cp sshapp-manager.jar \
     -Dloader.path=/workspace/_oratest -Dloader.main=OraTest \
     org.springframework.boot.loader.PropertiesLauncher 169.169.50.1 DBSERVER
# 期望: [OK] ... Oracle Database 11g Enterprise Edition Release 11.2.0.4.0
```

### 顺带查出的两个配置错误
| 项 | 错误值 | 正确值 | 怎么发现的 |
|---|---|---|---|
| 主机 | `169.169.50.4:1521` | `169.169.50.1:1521` | 端口探测 `.50.4` 已关闭 |
| 服务名 | `DBSERVER1` | `DBSERVER` | 枚举 22 个候选名，只有 DBSERVER 命中 |

### 可复用结论
> 1. 注入 fat jar 一律 `jar uf0`，注入后看 `unzip -v` 的 Method 列必须是 `Stored`。
> 2. 改 jar 前必须备份，且**先恢复服务、再改第二遍**——不要边改边赌。
> 3. 验证驱动能加载，要用 `PropertiesLauncher` 实跑一次，而不是 `unzip -l` 看到文件名就算。
> 4. Oracle 报 `ORA-12505/12514` 不是账号问题，是 SID/服务名不对；写个小程序枚举候选名比问人快。
