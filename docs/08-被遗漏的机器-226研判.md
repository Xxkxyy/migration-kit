# 08 · 被遗漏的第 6 台机器（.226）研判

> 迁移收尾时才发现还有一台高度相关的机器。这里记录**如何给一台"来路不明"的服务器定性**，
> 以及本案结论。方法是通用的，可直接套到别的漏网机器上。

---

## 一、定性方法：五个问题，按顺序问

| # | 问题 | 命令 | 判断依据 |
|---|---|---|---|
| 1 | 它现在在跑什么？ | `ps -eo pid,etime,rss,args --sort=-rss \| head -20`、`ss -lntup` | 有 java/node/python 业务进程吗？监听业务端口吗？ |
| 2 | 容器里有什么？ | `docker ps -a --format '{{.Names}}\|{{.Image}}\|{{.Status}}\|{{.CreatedAt}}'` | 状态 + **创建时间**能还原历史 |
| 3 | 它跟谁通讯？ | `ss -tnp state established`、配置里的 IP grep | 出向连接 = 真实依赖 |
| 4 | 谁依赖它？ | 在其他机器上 `grep -rl <本机IP>` | 没人依赖 = 叶子节点，可下线 |
| 5 | 数据值多少？ | `du -sh`、`find -size +1G` | 区分"运行态"与"历史归档" |

**关键经验**：`docker ps -a` 的 `CreatedAt` 比 `Status` 有用得多。
本案就是靠创建时间（2021-11 / 2022-06 / 2022-11）还原出"三次搬迁"的历史。

## 二、本案结论（169.169.50.226，主机名 hulianjiance）

## 三、迁移可行性判定

| 资产 | 判定 | 理由 | 处理方式 |
|---|---|---|---|
| 15 个停用容器 | ❌ 不迁 | 业态已被 222~225 取代；2022 那次重启是失败的 | `docker inspect` 导出留档 |
| 2022-11 MySQL 数据目录 320G | ⚠️ 归档 | 唯一且比备份新；但不是当前生产数据（当前在 196） | `tar cz` 流式压缩后传 196 |
| 2021 备份 319G + tar 44G | ⚠️ 只留压缩版 | 两者是同一份 | 只归档 44G 的 tar |
| prometheus | ✅ 可迁 | 数据 1.3G，配置简单 | 但 target 全是旧机，迁过去无意义 → 建议在新环境重建 |
| node_exporter | ✅ 重装 | 一个二进制 + systemd | 新机 `dnf install`/二进制 |
| grafana | ❌ | 停 2 年 | 需要时再起 |
| **InfoeyeAgent** | ❌ **不能自查迁** | 第三方安全 agent，需厂商注册授权 | 找安全/厂商在新机部署，旧机解绑 |
| libvirtd / GNOME | ❌ | 无虚拟机、桌面无人用 | 忽略 |

## 四、三个方案

### 方案 A（推荐）· 只归档、不迁运行

```bash
# 1) [196] 建归档目录（2T 还有 970G）
mkdir -p /data/archive/226

# 2) [226] 压缩流式传输（不落地临时文件）
tar -C /home/eking/docker-scloud/mysql/mysql -czf - mysql \
  | ssh root@169.169.51.196 'cat > /data/archive/226/mysql-data-20221115.tar.gz'

# 3) [226] 配置与部署留档（几十 MB）
tar -C /home/eking/docker-scloud -czf - SingleCfg.env eking/conf busi/conf \
    */docker-compose.yaml */environment.env \
  | ssh root@169.169.51.196 'cat > /data/archive/226/conf-backup.tar.gz'

# 4) [226] 2021 备份压缩版（44G，已有压缩）
rsync -a /home/dataspace/xtrabackup_202111100130.tar.gz root@169.169.51.196:/data/archive/226/

# 5) 校验（两侧字节数一致）
ls -l /data/archive/226/
```

之后 226 只等两件事：**厂商解绑 agent** → 关机保留观察 1~2 周 → 下线。

### 方案 B · 整体封存
不动任何东西。缺点：CentOS 7 长期在线（合规风险）、707G 占着、agent 授权继续占用。

### 方案 C · 只迁监控
把 `monitor/` 拷到 197 重建 prometheus，targets 改成 196~201。适合"还想继续看监控"的场景。

## 五、本案给同行的三条结论

1. **`docker ps -a` 的 CreatedAt 是考古利器**——能还原"什么时候被谁取代"，比问人快。
2. **判断能否下线，只看两点**：有没有出向业务连接（`ss -tnp`）、有没有人配置里引用它（`grep -rl`）。两者皆无 = 叶子节点。
3. **"备份"和"数据目录"要分开算**：本案 319G 备份与 44G tar 是同一份，320G 数据目录才是唯一增量。
   不做这个去重，会白搬 300G。
